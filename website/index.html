What is Astral Orchestrator?

A small flight crew for every bigger request.

It is a local, open-source plugin for Codex. Instead of one session doing everything at once, your request travels with a crew: a captain who owns the plan, specialists who fly their leg, and an inspector who signs off before landing. No API key, no project-operated backend, no analytics. Just a steadier way of working.

Sol plans the route

One lead turns your request into an outcome, a plan, and safety boundaries. Sol stays responsible for the final call instead of drifting mid-conversation.

Specialists do the work

Narrow, repeatable pieces go to Luna. Context-heavy implementation goes to Terra. Each worker receives a bounded packet instead of your whole conversation history.

A fresh review signs off

Checks run against the actual changes first. Then a separate Sol reviewer, with no stake in producing the work, decides whether it is ready to hand back.

Pick an altitude

Six modes, one steady hand.

Tell Astral how careful to be. It raises safeguards when a request is riskier than the mode you picked, and it never broadens the work you asked for.

Quick

Tiny and reversible

Sol works directly and self-reviews at the configured effort. No delegation and no ceremony, just the explicit single-session option for small jobs.

Best for: obvious, easy-to-undo changes.

Guided · default

Plan, delegate, verify

Sol plans, Luna or Terra implements bounded work, and a fresh Sol review checks the result. The everyday route for real project work.

Best for: normal changes and projects.

Careful

Maximum scrutiny

A visible plan, confirmation gates, pinned workers, strict verification, and read-only reviewer evidence for high-stakes work.

Best for: credentials, payments, production, migrations.

Measured · opt-in

Slower by design

A deliberately slower, evidence-oriented route for an explicit request. It is never auto-selected; Guided remains the default for normal work.

Best for: a reproducible record of a route decision and its checks.

Morph · explicit

Choose the worker route

Morph uses an explicitly selected worker model and effort when the host can provide that capability; the route is capability-dependent. The provider may be external, and a fresh review is required before handoff.

Best for: a deliberate provider or capability choice.

Constellation · capacity-aware

Parallel first wave, when safe

Constellation starts a cost-aware parallel first wave only for independent, non-overlapping cards within host-advertised capacity. One primary consumes a slot; no extra Sol implementers run by default.

Best for: parallelizable work with a proven serial fallback.

Automatic primary checker

Astral first looks for allowlisted local model/effort evidence. If evidence is absent, it can use a one-time user confirmation; mismatch or invalid evidence blocks the route. Morph does not claim every provider has native effort semantics, and Constellation does not claim every host supports multi-agent orchestration: when capacity or independence is uncertain, use the serial fallback.

How it works

One lead, the right lane, then a fresh look.

The usual Guided or Careful route, step by step. Sol keeps the outcome and safety boundaries; Luna and Terra receive bounded work only after that plan is settled.

Tap a step to open it. Every lane is touch-friendly.

01 Sol leads the plan Your request becomes a clear outcome, a plan, and safety boundaries.

Sol settles requirements, architecture, and what done means before anyone writes a line. Guided and Careful work must run on the configured Sol route at the configured effort. If that route cannot be proven, Astral stops rather than quietly substituting another model.

Sol hands off bounded work
02 Luna takes narrow work Focused, repeatable tasks with a settled instruction.

Think of a rename, a small transform, or a tight template: fully specified and easy to verify. Luna receives a bounded packet, not your whole conversation, at its configured effort.

02 Terra takes context-heavy work Broader implementation, integration, and debugging.

When the work needs project context, like wiring a feature, chasing a bug across files, or careful refactoring, Terra steps in after Sol has settled the plan, at its configured effort.

03 Checks run, then a fresh Sol review The actual changes are inspected before anything comes back to you.

Relevant checks run against the real diff. Then a separate Sol reviewer, with no stake in producing the work, assesses the finished result. Careful mode adds confirmation gates and read-only review evidence.

The route is a documented heuristic based on the work at hand. Every lane runs its pinned model at its configured effort, and a mismatched lane is blocked and explained instead of hidden.

Measured mode

Freeze the plan. Keep the evidence.

Measured is an explicit opt-in route, not a claim that every task needs more process. It creates a deliberate, inspectable record while Sol keeps the requirements, architecture, and final decisions.

One fixed card, one selected lane

Sol freezes one canonical work card and named acceptance checks, then uses deterministic Sol/Luna/Terra routing at the configured efforts. Only the selected implementation lane edits the bounded card.

Ambiguity gets the same question

Only a genuine Luna/Terra routing ambiguity can trigger optional, identical read-only probes. They receive the same frozen card and checks; Sol records the decisive facts and keeps the final route decision.

Resumable proof, then a fresh look

Measured keeps private, resumable evidence locally without secrets, raw prompts, or a project-operated service. Frozen checks run on each attempt, and a fresh Sol review supplies the final verdict.

OpenRouter’s Ori Eval and its reproducible evaluation skill inspired the pinned/reproducible evaluation and state-tracking method. Astral does not run Ori or OpenRouter and adds no OpenRouter runtime or API dependency.

A distinct check before handoff

Splitting planning, doing, and checking means the reviewer had no hand in the work it judges. Route proof blocks silent model or effort swaps, so the workflow you configured is the one that actually runs.

Evidence you can reproduce

The chart regenerates from one command in benchmarks/. Read the benchmark guide and inspect the committed context-footprint JSON. The local scorecard runs locally on your supplied trials; it can assess them, but it is not a standing product-performance claim.

Honest scope: these static instruction-context measurements do not measure task quality, latency, price, or total-run tokens. They do not by themselves prove that every orchestrated run uses fewer total tokens.

The current repository verification passed 100+ automated tests and package verification. This validates behavior and contracts: progressive context loading, exact pinned routes, objective checks plus fresh review, and a local privacy/no-analytics runtime posture. It does not prove Astral beats single-Sol.

The first end-to-end pilot is retained as invalid exploratory evidence after fresh review found protocol defects. Read the invalid-pilot disclosure. No valid outcome comparison exists. This page does not publish outcome, token, time, or quality numbers from that pilot.
